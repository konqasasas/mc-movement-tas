# 問題ファイル形式と判定の定義(v1)

この文書は、エンジンに渡す「問題」と、エンジンが返す「解答」の形式、そしてタイムの数え方を厳密に決めます。対象は Minecraft Java Edition 1.12.2 です。実装は `problem` モジュールにあります。

## 1. 用語

| 用語 | 意味 |
| --- | --- |
| ティック | ゲームの1更新。1/20秒。 |
| 位置 `p_t` | ティック `t` の移動処理が終わった直後のプレイヤー座標 `(posX, posY, posZ)`。足元の中心で、F3 に出る値と同じ。 |
| 入力 `u_t` | ティック `t` に有効なキー集合と視点角度。 |
| スタート直方体 `S` / ゴール直方体 `G` | 問題ファイルが与える軸に平行な直方体。 |

## 2. ティックの数え方

- `p_0` はスポーン地点そのものです。プレイヤーはここに静止して立っています(地上、速度は `(0, -0.0784000015258789, 0)`、スプリントなし、ジャンプのクールダウンなし)。
- 入力列の1行目が `u_1` です。ティック `t` では、`u_t` のキーと角度を設定してから1ティック分の移動処理を行い、その結果が `p_t` です。
- 角度 `yaw` と `pitch` は毎ティックの絶対値(float)です。マウスで出せる値かどうかは問いません。
- これは PKC の行インデックスと次の対応になります: 解答の `u_t` は PKC の `rows[t-1]` です。

## 3. スタートとゴールの判定

点 `p` が直方体 `B` に入っているとは、3軸すべてで `B.min <= p <= B.max` が成り立つことです(境界を含む)。プレイヤーの当たり判定の箱ではなく、座標の点だけで判定します。

- **スタートの侵入**: `t >= 1` で `p_t ∈ S` かつ `p_{t-1} ∉ S` のとき、ティック `t` にスタートへ侵入したとします。スポーン地点が `S` の中にある場合だけ、`t = 0` も侵入として数えます。
- **ゴール**: スタートへの侵入が1回以上あった後で、初めて `p_t ∈ G` となったティックを `T_g` とします。
- **計測開始**: `T_g` より前の最後のスタート侵入ティックを `T_s` とします。スタートから出て入り直すと、計測はやり直しになります。
- **タイム**: `T_g - T_s` ティックです。秒にするには20で割ります。
- スポーンからスタートまでの助走は自由で、タイムに入りません。

失敗の条件は次の3つです。

- `p_t.y < voidY` になった(奈落に落ちた)
- `limits.maxTicks` ティック以内にゴールしなかった
- 入力列が尽きた

`S` と `G` が重なる問題は読み込み時に拒否します。

### 実機との関係

判定はクライアント側の移動処理の結果そのもので行います。サーバーに送られる位置パケットは、移動量が小さいと送られないことがあるため、サーバー側のプラグインで計ったタイムとは一致しない場合があります。

## 4. 問題ファイル(`*.problem.json`)

```json
{
  "format": "mctas-problem",
  "version": 1,
  "id": "v0/04-gap-3",
  "title": "3ブロックの隙間を跳ぶ(4bジャンプ)",
  "mcVersion": "1.12.2",
  "world": {
    "source": "inline",
    "fills": [
      {"from": [0, 64, -30], "to": [0, 64, 0], "block": "minecraft:stone"},
      {"from": [0, 64, 4], "to": [0, 64, 4], "block": "minecraft:stone"}
    ]
  },
  "spawn": {"pos": [0.5, 65.0, -29.5], "yaw": 0.0, "pitch": 0.0},
  "start": {"min": [-1.0, 60.0, 0.0], "max": [2.0, 70.0, 1.0]},
  "goal": {"min": [-0.3, 65.0, 3.7], "max": [1.3, 65.0, 5.3]},
  "limits": {"maxTicks": 400, "voidY": 0.0},
  "target": {"ticks": 11, "kind": "upper_bound", "witness": "04-gap-3.tas"}
}
```

| キー | 必須 | 意味 |
| --- | --- | --- |
| `format`, `version` | はい | `"mctas-problem"` と `1` か `2`(`player` を使うときは `2`) |
| `id` | はい | 問題の識別子 |
| `title` | いいえ | 人が読む名前 |
| `mcVersion` | はい | `"1.12.2"` のみ |
| `world` | はい | 下記 |
| `spawn` | はい | 足元の座標と、最初の向き |
| `start`, `goal` | はい | `min` と `max` で与える直方体(実数) |
| `limits.maxTicks` | いいえ | スポーンから数えた最大ティック数。既定 1200 |
| `limits.voidY` | いいえ | これより下に落ちたら失敗。既定 -64 |
| `target` | いいえ | 既知の目標タイム。`kind` は `upper_bound`(これ以下で解ける)か `optimal`(最適と証明済み)。`witness` はその入力列ファイル(問題ファイルからの相対パス) |
| `rules` | いいえ | `autoJump` は `false` だけを許します(1.12.2 の自動ジャンプはオフ前提) |
| `player` | いいえ | v2 のみ。下記。v1 では空でなければなりません |

### プレイヤーの持ち物(v2)

```json
"player": {
  "inventory": [{"slot": 0, "block": "minecraft:stone", "count": 64},
                {"slot": 1, "block": "minecraft:dirt", "count": 3}],
  "selectedSlot": 0
}
```

- `inventory` はホットバーの中身です。`slot` は 0〜8(数字キーの 1〜9)、`count` は 1〜64(省略すると 64)。書かなかったスロットは空です。
- 置けるのはフルブロックだけです(石、土、羊毛など。プロパティを持つブロック、落下・成長するブロック、右クリックで動くブロック(作業台、音符ブロック、シュルカーボックスなど)、コマンドブロック、バリア、スポナー、レッドストーンブロックは不可)。置けないブロックを書くとエラーになります。
- `selectedSlot` はスポーン時に持っているスロットで、既定は 0 です。
- オフハンドは空です。サバイバルなので、置くたびに 1 個減ります。

設置の扱いは 1.12.2 のクライアントと同じです。

- ドア、はしご、ベッド、看板、植木鉢、たいまつなど支えの要るブロックの隣に置くと、実機ではそのブロックが外れることがあります。エンジンのワールドは変わらないので、探索はこれらの隣に置かないでください(`BlockType.isFragile()`)。
- 視線はティックの初めの目の位置(前のティックの終わりの位置に、目の高さ 1.62、スニークの高さなら 1.54 を足したもの)から、そのティックの `yaw` と `pitch` の向きに 4.5 ブロック伸びます。当たったブロックの面の隣に置きます(雪、草など置き換えられるブロックに当たったときはその場所に置きます)。
- 右クリックは、押した最初のティックに 1 回、押し続けると 4 ティックごとに 1 回です。置いたブロックは同じティックの移動から当たり判定に入ります。
- プレイヤーの当たり判定と重なる場所には置けません。置けるかどうかは、クライアントとサーバーの両方が確かめます。サーバーはクライアントが最後に送った位置から当たり判定を作り直すので、クライアントの当たり判定とは最後の桁や、送られていない小さな動き(0.03 未満)の分だけずれます。クライアントだけが置けると判断した場合、実機ではブロックが一瞬見えてから消え、ホットバーの数もずれます。エンジンはこれを扱わず、`unsupportedAction` を立てます。サーバーがスニークの切り替えを反映し終えたか分からない間(切り替えを送ってから 3 ティック)は、立った高さとスニークの高さの両方で確かめます。
- スポーン時は、立ち止まった状態で位置を送り直した直後(20 ティックごとの再送の直後)とみなします。実機の再生はスポーンでこの瞬間を待ってから始めます。
- 作業台やチェスト、ドア、ボタンなど右クリックで動くブロックを、スニークせずに右クリックしたときは置きません。実機の記録 mod はこれが起きたランをその場で止めます。これはエンジンが扱わない動作なので、状態の `unsupportedAction` が立ちます(探索はこの状態を捨ててください)。ツタ、レッドストーンワイヤー、2 ブロックの高さの植物に視線が当たったときも同じです。

### ワールド

v1 は `"source": "inline"` だけを実装しています。`fills` は `/fill` と同じく両端を含む整数のブロック座標で、後に書いたものが上書きします。書かれていない場所はすべて空気です。

`block` には 1.12.2 のブロックステート文字列を書きます(例: `minecraft:oak_stairs[facing=north,half=bottom]`)。`minecraft:` は省略でき、プロパティの順番は自由です。当たり判定に関係しないプロパティ(色、木の種類、階段の `shape`、フェンスのつながりなど)は書いても無視されるので、F3 画面の表示をそのまま貼れます。階段の形やフェンスのつながりは、vanilla と同じく周りのブロックから計算します。

1.12.2 のブロックはすべて使えます。例外は `portal`、`end_portal`、`end_gateway`、`piston_extension`(動いている途中のピストン)だけで、これらはエラーになります。水と溶岩は `minecraft:water[level=0]` のように書きます(`flowing_water`、`lava`、`flowing_lava` も同じ形で、`level` は 0〜15)。ドアは上下 2 つの半分をそれぞれ書きます(F3 の表示どおり)。

当たり判定に関係するプロパティ(ハーフブロックの `half`、階段の `facing` と `half`、ドアの `facing`・`half`・`hinge`・`open` など)は省略できません。どのブロックがどのプロパティを必要とするかは、`physics/.../VanillaBlocks.java` と `physics/src/main/resources/.../vanilla-blocks.tsv` の `props` 行にあります。

物理エンジンが計算しないこと:

- ダメージ(サボテン、マグマブロック、炎、溶岩、落下)。実際のゲームではダメージを受けるとサーバーが速度を上書きするので、ダメージを受けるルートはずれます。
- 耕地を踏み荒らすこと。1.5 ブロック以上の高さから耕地に落ちると土に変わり、プレイヤーが押し上げられます(0.5〜1.5 ブロックでは確率)。
- 勝手に変わるブロック: 砂や砂利の落下、作物の成長、葉の消滅、感圧板・トリップワイヤー・ディテクターレールをプレイヤーが踏んで出る信号とそれで開くドアやピストンなど。エンジンのワールドは書いたとおりのまま動きません。

次の版で、1.12.2 のセーブデータ(Anvil 形式)から範囲を指定して読む `"source": "anvil"` を足す予定です。形は次を想定しています。

```json
"world": {"source": "anvil", "save": "saves/MyMap", "dimension": 0,
          "bounds": {"min": [-100, 0, -100], "max": [100, 128, 100]}}
```

範囲の外は空気として扱います。

### ゴール直方体の作り方(問題集の慣習)

「ブロックに着地する」をゴールにするときは、ブロック上面の高さちょうどを `y` の範囲にし(`min.y = max.y = 上面`)、水平方向はブロックの範囲を 0.3 ずつ広げます。着地したティックの `posY` は上面の値にぴったり一致し、当たり判定の箱(幅 0.6)がブロックに少しでもかかれば中心は広げた範囲に入るからです。空中で上を通過しただけでは `y` が一致しないので、ゴールになりません。

## 5. 入力列

### テキスト形式(`.tas`、手書き用)

```
# 行頭の数字は、その入力を何ティック続けるか
yaw 0
85 W SPRINT
1 W SPRINT JUMP
11 W A SPRINT yaw=45
1 - yaw=0
```

- `N キー… [yaw=角度] [pitch=角度]` で、同じ入力を N ティック続けます。`-` はキーなしです。
- `yaw=` と `pitch=` は、指定した行から後ろすべてに効きます。最初の値はスポーンの向きです。
- `yaw 角度` だけの行でも角度を変えられます。
- キーは `W A S D JUMP SPRINT SNEAK USE`。別名として `J`/`SPACE`、`R`/`CTRL`、`N`/`SHIFT`、`U`/`RMB` も読めます。`USE` は右クリック(設置)です。
- `slot=番号`(0〜8)で、その行のティックにホットバーのスロットを選びます。選んだスロットはそのまま続きます(次に `slot=` を書くまで)。
- `#` から行末まではコメントです。

### 解答ファイル(`*.solution.json`)

エンジンの出力です。入力は1ティック1行で、ゴールしたティックまでを含みます。

```json
{
  "format": "mctas-solution",
  "version": 1,
  "problem": "v0/04-gap-3",
  "mcVersion": "1.12.2",
  "result": {"status": "finished", "ticks": 11, "startTick": 88, "goalTick": 99,
             "model": "physics-1.12.2", "engineBuild": "3e71a53434154af2"},
  "inputs": [
    {"keys": ["W", "SPRINT"], "yaw": 0.0, "pitch": 0.0}
  ]
}
```

入力の各行の `keys` には `USE` が入ることがあり、ホットバーのスロットを選ぶ行には `"slot": 0`〜`8` が付きます(付かない行は選び直しなし)。PKC には右クリックとスロットがないので、設置を使う入力列は `--pkc` で書き出せません。

`status` は `finished`、`not_finished`、`fell_into_void`、`too_long` のどれかです。`model` は時間を計算した物理の名前です。

`engineBuild` は解答を作ったエンジンのビルド ID です。`physics` のソースと表、`problem` のソース(`cli` と `baseline` を除く)から計算したハッシュで、`physics/src/main/resources/.../engine-build.txt` に入っています。同じ入力列でも、物理や入力の読み方が変わると結果が変わるので、ID の違う解答は次のように扱います。

- `mctas-problem time` は警告を出して、今のビルドで計算し直します。`--strict` を付けると拒否します(終了コード 3)。
- `/mctas replay` は拒否します。末尾に `force` を付けると再生します。
- `engineBuild` のない古い解答と `.tas` は、警告だけ出して受け付けます。

### PKC の保存形式への変換

`--pkc` を付けると、ParkourCalculatorMod でそのまま読める保存ファイル(PKC `SaveFile` の version 1)を書き出します。

- `start.pos` はスポーン座標、`start.vel` は静止時の `(0, -0.0784000015258789, 0)`、`start.yaw` と `pitch` はスポーンの向き
- `rows[t-1]` が `u_t` で、`keys` は同じ名前、`yaw` は `yawLocked: true` の絶対値

ワールドそのものは PKC の保存ファイルに入らないので、ゲーム内で同じブロックを置いた場所で読み込みます。

## 6. 時間の計算に使う物理

タイムは `physics` モジュールの `Physics.tick`(公式 1.12.2 のコードと照合済み)で計算します。`problem` 側では `MovementModel` を通して呼ぶので、物理を差し替えても判定の部分は変わりません。

PKC に入っている 1.12.2 の記録 `trp-optimize-feasible-swap.json` の平地区間で、位置、速度、接地、スプリントがビット単位で一致することを `PkcCaptureParityTest` で確かめています。PKC は途中で当たり判定の箱を座標から作り直すため、そのティックだけ同じ操作を入れると37ティックすべて一致します。

## 7. 問題集 v0

## 8. 将来の拡張のための予約

v2 でフルブロックの設置(`player.inventory`、入力の `USE` と `slot`)を足しました。次の拡張で、ポーション効果、ゲームモード、左クリック(破壊)を足す予定です。

## 9. コマンド

```
./gradlew :problem:installDist
problem/build/install/mctas-problem/bin/mctas-problem time problems/v0/04-gap-3.problem.json problems/v0/04-gap-3.tas
problem/build/install/mctas-problem/bin/mctas-problem time <問題> <入力> --trace --solution out.solution.json --pkc out.pkc.json
problem/build/install/mctas-problem/bin/mctas-problem check problems/v0
problem/build/install/mctas-problem/bin/mctas-problem search <問題> out.tas --beam 4000 --yaws 0,45 --via "0,64,4"
problem/build/install/mctas-problem/bin/mctas-problem score problems/v0 out-a/ out-b/ --markdown
```

- `time`: 入力列のタイムを計算します。`--trace` で毎ティックの座標を出します。
- `check`: フォルダ内の全問題について、`target.witness` の入力列が `target.ticks` ちょうどで解けるか確かめます。
- `search`: 目標タイムを作るための簡単なビームサーチです。最適解を探すものではありません。`--via` は途中で着地するブロックの座標です。
- `score`: 探索エンジンどうしの成績表です。解答フォルダ(エンジンごとに 1 つ、`*.solution.json`)の全解答を物理で計り直し、問題ごとに「ティック数(目標との差)計算時間」を並べます。計算時間は解答の `result.search.wallMillis`、列の名前は `result.search.engine` です。切り替えの 3 ティック規則を破る解答には `!` が付きます。最後に、解けた数と目標以下の数、全エンジンが解けた問題でのティック合計を出します。`optimal` の目標より速い解答があれば(物理か証明の誤り)エラーで終わります。
