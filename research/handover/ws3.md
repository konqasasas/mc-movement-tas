# 引き継ぎ: WS3 探索エンジン(2026-10-28)

- **済み**: `search` モジュール(PR #21)。上界はビームサーチ(`mctas-search beam`)、下界は抽象解釈(`mctas-search bound`)。v0 のうち 01・02・03・04・06・08・09 の最適を証明(F-102〜F-104)。09・10 の旧解の制約違反を見つけて差し替え(F-101)。05・07・10 は差が残る(F-105, F-106)。v1-full の下界は s2001 ≥ 58、s2007 ≥ 128、s2008 ≥ 47。
- **済み(続き)**: どのコースでも出る下界 `mctas-search speed`(`SpeedBound`、F-107)。realdev ex1〜ex6 = 131/141/13/130/155/236、stpt1 = 132、human6 も全問。状態からの下界 `SpeedBound.ticksFrom(x, 足の y, z, vx, vz)` を他方式の枝刈り・打ち切り用の API にした(使い方は `search/README.md`)。
- **済み(続き)**: 足場をたどる下界 `HopBound`(F-108)。`speed` は二つの大きい方を出す。登るコースで prism 288、verdure 260、tohell 274。着地した状態からの下界 `HopBound.ticksFromGround(x, 足の y, z)`、区間の下界 `new HopBound(problem, from, to).ticks()`。
- **済み(続き)**: F-108 の値は健全でなかった(着地は y を先に解くので位置が面から 1 ティックはみ出せる、F-109)。直したうえで、位置の範囲を時刻順に追う前向きの探索を足した(F-110)。prism 270、tohell 318、verdure 239。`mctas-search gap <問題> <解>` で、解の各着地で下界が残りを超えないか確かめられる。WS9 の解との差は ex1 357、prism 325、tohell 416 ティック。
- **済み(続き)**: 跳躍の始めの速さを前向きの探索に持たせた(F-111)。prism 312、tohell 369、verdure 244。着地の余裕を跳躍ごとに絞り、位置の範囲を 16 角形にした(F-113、prism 337、tohell 399、verdure 308)。区間ごとの下界と解の差 `mctas-search segments <問題> <解> --json out.json`(F-112)。WS10 の解の結果は共有フォルダ bounds/ws3/*.segments.json。
- **済み(続き)**: 半ブロックの段の横で跳ぶと次のティックに着地する(F-115)。速度の下界はこれを見落としていて、実コースの値が高すぎた(訂正済み)。はしご・液体・スタートからの跳躍にも速さの表を使う。区間ごとの差は WS9 の 4 本(remaining・ex2・ex5・ex6)と WS10 の 3 本を bounds/ws3/ に置いた。
- **済み(続き)**: はしごを足の高さの刻みと段階で扱う(F-117、高さ 6 のはしごの下界 7 → 40)。速く落ちるティックが横の段に乗る着地と浮いた着地を入れて健全にし、ゴールの締めを戻した(F-118, F-119)。93 本の解で unsound 0。
- **未対応**: 天井、フルブロック以外、滑る床、持ち物(ブロック設置)は下界のモデルで Unsupported。スタート前の不動点は、複雑なコースでは `--max-steps` の上限に当たる(v1-full の 5 問)。

## 次にやること(優先順。1 つ終えたら次へ進む)

1. D-005(ダメージを受けない・耕地を踏み荒らさない)を `Evaluator` と `time --strict` に入れる(2026-10-29 の依頼)。WS10 の `improve/Course.touchesHazard` と、funnel・planner の同じ判定を 1 か所にまとめて全方式で使う。solutions/ の全部の解を判定し直し、違反の一覧を共有フォルダに置いて各スレッドに知らせる。テストを足す。
2. 落ちる速さを位置ごとに持って、横の段に乗る着地(F-119)を締め直す。今は周りの列に 0.6〜4.52 低い面があれば、どの段の横でも速く落ちてきたことにできる。高い面からの長い落下のときだけ効くはずなので、生成コースと human6 で下がった分(g0003 47、verdure 65)の多くを取り戻せる見込み。
3. waza1 の解の遅い区間(bounds/ws3/waza1_breakdown.md)を WS10 に渡し続ける。h4 の始めの区間で降りずに済むかを確かめる。waza はほかのサーバーのコースなので、research と bounds/ws3/ には数字だけを書き、座標・ブロック配置・経路は書かない。
4. 平らな区間の下界を締める。足場の列は平らなコースで速度の下界にほぼ並んだ(ex6 230 / 236)が、位置を細かくしても変わらなかった(F-113)。ex6 の前向きの最短経路は頭打ちの下の 5 ティックのジャンプの連続で、実際の動きに近い(F-114)。次は realdev の他の問題(ex1・ex4)で `MCTAS_FWDPATH=1` の経路を見る。次は、前向きの探索に速度の下界を見込み(A* の推定)として入れ、二つを足し合わせられるようにする。ジャンプ後の最少滞空を場所ごとに持たせる。
5. 区間ごとの差を WS10 に渡し続ける。新しい解が solutions/ に出たら `segments` を回し、bounds/ws3/ に置く。必要なら区切り方(`--length`)や形式を WS10 と合わせる。
6. realdev・human6・waza1 で新しく解けた問題の下界を出し(waza1 h1 201・h3 149・h4 82、F-119)、`gap` で解が下界以上か確かめて、findings に書く。
7. `segments` を速くする(区間ごとに世界全体の節点を作り直している。はしごの刻みで頂点が増え、waza1h4 では 1 区間 1〜2 分かかる)。
8. WS11(後ろ向き探索)が `ticksFromStart` の形を具体的に決めたら合わせる(今は着地点ごとの値を返すだけ。表をまとめて渡す形や、速さごとの値が要るかもしれない)。
