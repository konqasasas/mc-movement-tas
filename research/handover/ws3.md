# 引き継ぎ: WS3 探索エンジン(2026-10-28)

- **済み**: `search` モジュール(PR #21)。上界はビームサーチ(`mctas-search beam`)、下界は抽象解釈(`mctas-search bound`)。v0 のうち 01・02・03・04・06・08・09 の最適を証明(F-102〜F-104)。09・10 の旧解の制約違反を見つけて差し替え(F-101)。05・07・10 は差が残る(F-105, F-106)。v1-full の下界は s2001 ≥ 58、s2007 ≥ 128、s2008 ≥ 47。
- **済み(続き)**: どのコースでも出る下界 `mctas-search speed`(`SpeedBound`、F-107)。realdev ex1〜ex6 = 131/141/13/130/155/236、stpt1 = 132、human6 も全問。状態からの下界 `SpeedBound.ticksFrom(x, 足の y, z, vx, vz)` を他方式の枝刈り・打ち切り用の API にした(使い方は `search/README.md`)。
- **済み(続き)**: 足場をたどる下界 `HopBound`(F-108)。`speed` は二つの大きい方を出す。登るコースで prism 288、verdure 260、tohell 274。着地した状態からの下界 `HopBound.ticksFromGround(x, 足の y, z)`、区間の下界 `new HopBound(problem, from, to).ticks()`。
- **済み(続き)**: F-108 の値は健全でなかった(着地は y を先に解くので位置が面から 1 ティックはみ出せる、F-109)。直したうえで、位置の範囲を時刻順に追う前向きの探索を足した(F-110)。prism 270、tohell 318、verdure 239。`mctas-search gap <問題> <解>` で、解の各着地で下界が残りを超えないか確かめられる。WS9 の解との差は ex1 357、prism 325、tohell 416 ティック。
- **次**: 下界を締める。足場の列の下界は跳躍ごとに最高速から始めてよいとしているので、跳躍の始めの速さを状態に持たせる。実コースではジャンプ後の最少滞空が世界全体の最小(頭打ちで 1〜2)に引っ張られるので、場所ごとの滞空や高さの区間を経路グラフ(WS9)と組み合わせる。05・07・10 の完全な証明は、その副産物として締められる場合だけ。
- **未対応**: 天井、フルブロック以外、滑る床、持ち物(ブロック設置)は下界のモデルで Unsupported。スタート前の不動点は、複雑なコースでは `--max-steps` の上限に当たる(v1-full の 5 問)。
