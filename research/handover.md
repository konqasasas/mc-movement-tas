# 引き継ぎメモ

ワークストリームごとに、今どこまで進んでいて、次に何をするかを書きます。自分の節だけを上書きしてかまいません。

## WS2 物理・記録 mod(2026-10-28)

- **済み**: 1.12.2 のプレイヤー物理(全ブロック、水と溶岩。ポータル類を除く)が公式コードと実機の両方でビット単位で一致(F-001, F-006)。`/mctas replay` で解答を実機再生できる(F-007)。解答ファイルにエンジンのビルド ID を書き、ID の違う解答の再生を拒否する。
- **完了**: フルブロック設置。実機確認済み(E-011 で不一致 0。ユーザー了承 2026-10-28)。物理・公式コード照合(F-009, F-010)、問題形式 v2 の `player.inventory`、入力の `USE` と `slot`、mod の再生と照合(`/mctas fuzz place`、`/mctas replay` でホットバーを配る)まで実装済み。実機確認用の問題は `problems/place/01-pillar-2`。2 回目の実機ファズ(E-008)の唯一の不一致はサーバー側の設置判定(F-012)で、エンジンがサーバーの判定も見るように直した。3 回目(E-010)は設置の不一致 0。残ったのは、低い天井の下でスニークを離したときのサーバーの位置戻し(F-013、D-011)。
- **WS3 との取り決め**: `PlayerState.placed`(置いたブロックの差分、置いた順)、`state.world(base)` で差分を重ねたワールド、`equals` と `hashCode` は置いたブロックも含む、設置は (ワールド, 状態, 入力) だけで決まる。
- **保留**: mod の pitch が勝手に下がる現象(Q-003)。

## WS5 ワールド取り込み(2026-10-28)

- **済み**: `mctas-problem import`(1.12.2 のセーブと `.schematic` から範囲を切り出して inline の問題ファイルに)、`mctas-problem diffworld`、mod の `/mctas mark`・`/mctas export`・`/mctas checkids`。数値 ID の表は 1.13 の変換表と一致(F-014)。v0 の 10 問をセーブに書いて取り込み直すと、ワールドも目標タイムも一致する(`WorldImportTest`)。コードは `problem/.../cli/importer/` にあり、エンジンのビルド ID には入らない(既存の解答はそのまま使える)
- **確認済み**: 実機での表の照合(E-012、F-018)。mod はユーザーの環境でビルド・動作した
- **確認済み**: セーブ取り込みとゲーム内書き出しが一致(E-013、F-019)
- **未確認**: 取り込んだ問題の解の実機再生(E-013 の残り)。探索(WS3)の解ができたら試す
- **方針**: 問題形式に `"source": "anvil"` は足さず、取り込みは inline の `fills` に書き出す。問題ファイルだけで完結し、セーブがなくても採点・再生できるため

## WS3b 近似探索(2026-10-28)

- **済み**: `approx` モジュール(経路グラフ、手書き方策による先読み、ティック単位のビーム、経路 3 本)。採点コマンド `mctas-problem score`、`ToggleRule`、解答の `result.search`。問題集 `v1-dev`(調整用)、`v1-holdout`(報告専用)、`v1-full`(石だけ、WS3 の最適値で品質を測る用)と生成器 `mctas-approx gen`。成績は F-016。
- **次**: `Refiner`(区間ごとの再探索と向きの微調整、今は何もしない)。v0/08 の +1。v1-full の最適値が WS3 から出たら差を測る。新しい最良解を実機の `/mctas replay` で確かめる。
- **測り方**: 調整は `v1-dev` だけで行い、報告は `v1-holdout` と `v1-full` の `score` の表で出す。採用した改良には approx/README.md の版表に版を振る。

## WS8 局所テクニック(2026-10-28)

- **済み**: モジュール `technique`。区間の局所探索 `SegmentSearch`(厳密物理のティック単位ビーム、視点自由、粗いセルで併合、D-004 を区間内で守る)、マクロ行動の入口 `Technique.solve`(着地面 `Target`、(ティック数, 出口の速さ) のパレート集合、`ticksSinceLastToggle` の引き継ぎ。形は WS9 と合意)、段差の踏み切りの窓 `StepWindow`。stpt1 の段差 3 区間で近似の状態から 30 ティック縮む(F-029)、踏み切りの窓(F-030)
- **済み(続き)**: 近似の解のスタート直後からゴールまで局所探索すると stpt1 は 191 ティック(F-401、`technique/stpt1/stpt1-191.tas`)
- **確認済み**: 191 の解は実機でも全ティック一致(F-402)
- **済み(続き)**: 助走の探索(`runup`)で stpt1 をスポーンから 187(F-403)。梯子の表(F-404)。ネオ(F-405)。天井下の連続ジャンプ(F-406)。角(F-407)。軽いモード `Options.fast()`
- **済み(続き)**: 187 の解も実機で確認(F-408)。realdev の詰まる区間(つた・塀の柱・1 ブロックのはしご・水柱)を `region` で通した(F-409)。後ろへ戻る区間用に `Technique.chain`(途中の着地面を順に)
- **次**: (1) トラップドア(開いた板)の表。形が多いので、どの形を使うかを WS9 と決める。(2) 187 の解を実機で確かめる。(3) 探索の速さ(1 区間 50〜85 秒、幅 20000)。物理の高速化(PR #38)と区間ごとの行動の絞り込みで縮める。(4) 角の区間では道に沿った距離で並べる出口を、プランナーの経路から作る
- **注意**: 全コースを 1 回で探すと遅い(stpt1 で 6 分、F-401)。幅 5000・向きのずれ 0 だけでは人間に届かない(F-029)

## WS7 物理の高速化(2026-10-28)

- **済み**: 探索型の負荷で約 2.2 倍(F-301)。結果はビット単位で同じ。公開 API は変えていない(`BlockWorld` に既定メソッド `mayContainLiquid` を足しただけ)。速さとチェックサムは `./gradlew :problem:bench` で測れる。CI(`.github/workflows/build.yml`、PR #36)
- **次の候補**: (1) 探索側のメモリ。状態 1 つは約 240 バイトで縮める余地が小さい。木の親をたどるノードが `PlayerState` を持ち続けていると、ビームの外に出た状態も残る。親のノードからは状態を外し、入力だけを残すと大きく減る。(2) 複数スレッドでの展開。`Physics.tick` は状態を書き換えず、ワールドを書き換えなければ並列に呼べる。(3) 公式 jar との差分ファズ(`:oracle:fuzz`)をユーザーの環境で走らせる

## WS3 探索エンジン(2026-10-28)

- **済み**: `search` モジュール(PR #21)。上界はビームサーチ(`mctas-search beam`)、下界は抽象解釈(`mctas-search bound`)。v0 のうち 01・02・03・04・06・08・09 の最適を証明(F-102〜F-104)。09・10 の旧解の制約違反を見つけて差し替え(F-101)。05・07・10 は差が残る(F-105, F-106)。v1-full の下界は s2001 ≥ 58、s2007 ≥ 128、s2008 ≥ 47。
- **済み(続き)**: どのコースでも出る下界 `mctas-search speed`(`SpeedBound`、F-107)。realdev ex1〜ex6 = 131/141/13/130/155/236、stpt1 = 132、human6 も全問。状態からの下界 `SpeedBound.ticksFrom(x, 足の y, z, vx, vz)` を他方式の枝刈り・打ち切り用の API にした(使い方は `search/README.md`)。
- **次**: 下界を締める。実コースではジャンプ後の最少滞空が世界全体の最小(頭打ちで 1〜2)に引っ張られるので、場所ごとの滞空や高さの区間を経路グラフ(WS9)と組み合わせる。05・07・10 の完全な証明は、その副産物として締められる場合だけ。
- **未対応**: 天井、フルブロック以外、滑る床、持ち物(ブロック設置)は下界のモデルで Unsupported。スタート前の不動点は、複雑なコースでは `--max-steps` の上限に当たる(v1-full の 5 問)。
